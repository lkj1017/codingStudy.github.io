# 티스토리 수익형 콘텐츠 생성 에이전트 계획서

- 대상 블로그: lifegoals001.com (티스토리, 애드센스 승인 완료)
- 문체 후처리: [epoko77-ai/im-not-ai](https://github.com/epoko77-ai/im-not-ai) `humanize-korean` v2.3.2 (MIT)
- 실행 환경: Claude Code (im-not-ai가 Claude Code 플러그인이라 같은 런타임으로 묶는다)
- 작성일: 2026-10-24

---

## 0. 한눈에 보기

키워드를 고르면 에이전트가 리서치, 아웃라인, 초안, 사실 검증, im-not-ai 윤문, 티스토리용 HTML·SEO 패키지까지 만들어 "검토 대기함"에 넣는다. 사람은 글 하나에 10~15분을 쓴다. 경험 한두 줄과 사진을 보태고, 읽어 본 뒤 발행한다.

완전 무인 발행으로 설계하지 않은 이유는 두 가지다.

1. 티스토리 공식 Open API가 2024년 2월에 종료돼서 정식 자동 발행 경로가 없다.
2. 구글은 AI 글 자체를 막지 않지만, 가치를 보태지 않은 글을 대량으로 찍어내는 행위는 스팸 정책(scaled content abuse)과 애드센스 저가치 콘텐츠 정책에 걸린다. 걸리면 검색 유입과 광고 게재가 같이 무너진다. 사람 검토와 1차 경험 입력이 이 위험을 막는 장치다.

im-not-ai는 글을 새로 쓰는 도구가 아니다. 사실·수치·주장은 그대로 두고 번역투와 AI 관용구만 걷어내는 윤문기다. 그래서 파이프라인에서 "초안과 사실 검증이 끝난 뒤, HTML로 바꾸기 전"에 둔다. 문체를 다듬는다고 글의 가치가 생기지는 않는다는 점도 기억해 둔다. 가치는 리서치 품질과 사람의 경험에서 나온다.

## 1. 확인된 전제와 제약

| 항목 | 확인 내용 | 계획에 주는 영향 |
|---|---|---|
| 티스토리 API | 2024년 2월 Open API 글쓰기 종료. 지금 돌아다니는 자동 포스팅 도구는 로그인 세션을 쓰는 비공식 방식 | 기본은 "HTML 복사→붙여넣기". 브라우저 자동화는 임시저장까지만, 선택 사항으로 |
| 구글 스팸 정책 | 생성 방식이 아니라 "대량 + 낮은 부가가치 + 순위 조작 목적"을 본다. 기준 편수는 공개하지 않음 | 하루 1편 이하, 글마다 1차 정보(경험·사진·직접 계산) 최소 1개 |
| 애드센스 | AI 보조 글은 허용. 저가치·복제 페이지에는 광고 게재 제한 | 발행 전 품질 게이트, 출처 문장 복붙 금지 |
| im-not-ai | 10개 카테고리 85개 패턴 탐지 후 윤문. `장르: 블로그` 지원. 변경률 30% 경고, 50% 중단. `verify_gates.py`가 수치·고유명사 보존을 코드로 검사 | 초안 단계에서 quick-rules를 미리 적용해 light(1콜) 경로로 끝나게 유도 |
| 블로그 현황 | 이번 작업 환경 네트워크 정책 때문에 lifegoals001.com에 접속하지 못함 | 주력 카테고리와 기존 글 목록은 0주차에 직접 받아서 반영 (13장 결정 사항) |

## 2. 목표와 KPI

수익은 대략 `월 페이지뷰 × 페이지 RPM ÷ 1000`이다. 트래픽과 RPM(키워드 단가)을 같이 끌어올리는 게 목표고, 새 글이 구글에 자리 잡기까지는 보통 몇 달이 걸린다고 보고 지표를 단계별로 잡는다.

| 시점 | 지표 | 목표 |
|---|---|---|
| 1개월 | 발행 편수 / 글당 사람 작업 시간 | 15~20편 / 15분 이하 |
| 1개월 | 색인율 (Search Console) | 발행 글의 80% 이상 색인 |
| 3개월 | 검색 노출·클릭, 10위 안 키워드 수 | 월별 우상향, 10위 안 키워드 20개 이상 |
| 3개월 | 카테고리별 RPM | 상위 RPM 카테고리를 찾아 비중 확대 |
| 상시 | 품질 | im-not-ai 등급 A/B 비율 90% 이상, 사실 오류 신고 0건 |

## 3. 전체 구조

```
[주 1회] /plan-week
   Search Console·지난주 성과 + 키워드 리서치 ──▶ data/backlog.csv (사람이 주제 승인)
                                                        │
[매일·격일] /new-post "키워드"                            ▼
   ① 브리프 ─▶ ② 리서치 ─▶ ③ 경험 입력(사람, 선택) ─▶ ④ 아웃라인 ─▶ ⑤ 초안
                                                                     │
   ⑨ QA 게이트 ◀─ ⑧ 티스토리 HTML·SEO ◀─ ⑦ im-not-ai 윤문 ◀─ ⑥ 사실 검증
        │
        ▼
   검토 대기함 (로컬 폴더 / GitHub PR / Notion 중 택1)
        │  사람: 읽기·사진 추가·승인 (10~15분)
        ▼
   ⑩ 발행 (티스토리 에디터 HTML 모드 붙여넣기 → 예약 발행)
        │
        ▼
   ⑪ 사후 처리: published.json 갱신, Search Console 색인 요청

[주 1회] /weekly-report ─▶ 리라이트 후보(/refresh-post), 다음 주 주제에 반영
```

## 4. 파이프라인 단계별 설계

| 단계 | 담당 | 입력 → 출력 | 통과 조건 |
|---|---|---|---|
| ① 브리프 | 오케스트레이터 | 키워드 → `00_brief.md` (검색 의도, 글 유형, 타깃 독자, 경쟁 글 요약) | 같은 키워드가 `published.json`에 없을 것 |
| ② 리서치 | `researcher` 서브에이전트 | 브리프 → `01_research.md` (사실 목록, 출처 URL, 확인 날짜) | 핵심 사실마다 출처 1개 이상. 정부·기관 공식 자료 우선 |
| ③ 경험 입력 | 사람 (질문은 에이전트가 생성) | 질문 3개 → `02_experience.md` | 비어 있으면 "경험 없음"으로 표시하고 정보형으로만 작성 |
| ④ 아웃라인 | `writer` | 브리프+리서치+경험 → `03_outline.md` (제목 후보 3개, H2/H3, 표·FAQ 위치) | 상위 노출 글과 다른 점 1개 이상 명시 |
| ⑤ 초안 | `writer` | 아웃라인 → `04_draft.md` | `config/style-guide.md` + im-not-ai `quick-rules.md`를 미리 지켜서 작성 |
| ⑥ 사실 검증 | `fact-checker` | 초안+리서치 → `05_factcheck.md`, 수정된 초안 | 수치·날짜·금액·조건이 리서치와 일치. 근거 없는 문장은 삭제하거나 "확인 필요"로 표시 |
| ⑦ 윤문 | `/humanize-korean` (im-not-ai) | 검증된 초안 → `06_humanized.md` | `verify_gates.py` exit 0, 또는 exit 1 + finalize 통과. 등급 A/B |
| ⑧ 포맷 | `seo-editor` + `md_to_tistory.py` | 윤문본 → `post.html`, `meta.json` (제목, 설명, 태그, 카테고리, 대표 이미지 alt) | 내부 링크 2~3개, 제목 키워드 앞쪽 배치 |
| ⑨ QA | `qa_check.py` (LLM 없이 코드로) | `post.html` → `qa.json` | 아래 체크리스트 전부 통과 |
| ⑩ 발행 | 사람 | 검토 후 붙여넣기 | 사람 승인 없이는 공개 발행하지 않음 |

### ⑦ im-not-ai 연결 방법

- 설치: 프로젝트 `.claude/settings.json`에 마켓플레이스와 플러그인을 등록해 로컬·클라우드 어디서 열어도 같은 버전이 깔리게 한다. 수동 설치라면 `/plugin marketplace add epoko77-ai/im-not-ai` → `/plugin install humanize-korean@im-not-ai`.
- 호출: `/humanize-korean 장르: 블로그` + 초안 경로. 오케스트레이터는 `_workspace/{run_id}/final.md`를 `06_humanized.md`로 복사한다.
- 경로 선택은 스킬의 `route_hint`에 맡긴다. ⑤에서 quick-rules를 미리 지키면 대부분 light(1콜)나 standard(2콜)로 끝나서 비용이 줄어든다.
- 게이트 처리:
  - exit 0 → 진행
  - exit 1 → finalize 결과까지 보고 진행, 경고 내용은 검토 대기함 메모에 남김
  - exit 2(변경률 50% 이상) → 윤문본 버리고 검증된 초안으로 1회 재시도, 또 실패하면 사람 검토로 넘김
  - 등급 C/D → `--strict`(heavy)로 1회 재실행, 그래도 C/D면 사람 검토
- 충돌 지점: im-not-ai는 과한 헤딩·불릿·볼드를 AI 티(C, J 카테고리)로 본다. 블로그 SEO에는 H2/H3와 표가 필요하다. 그래서 윤문 지시에 "헤딩과 표 구조는 유지"를 명시하고, 변경률이 헤딩 때문에 부풀었으면 `--ignore-markup` 수치를 함께 기록한다. `qa_check.py`에서 윤문 전후 H2 개수가 같은지도 확인한다.
- 버전 고정: 스킬이 자주 업데이트되므로 동작 확인한 버전(현재 2.3.2)을 `config/blog.yaml`에 적어 두고, 올릴 때는 샘플 글 3편으로 회귀 확인한다.

### ⑨ QA 체크리스트 (`qa_check.py`)

- 본문 길이가 유형별 범위 안 (예: 정보형 2,000~4,000자, `blog.yaml`에서 조정)
- H2 3~7개, 윤문 전후 개수 동일
- 남은 마크다운 기호, 깨진 HTML, 빈 링크 없음
- 챗봇 잔재 문구 없음 ("도움이 되셨길", "AI로서", "물론입니다" 등)
- 숫자·날짜가 `01_research.md`에 있는 값과 일치 (윤문 후 재대조)
- 출처 원문과 15어절 이상 연속 일치하는 문장 없음 (복붙 방지)
- 제휴 링크가 있으면 대가성 문구 포함
- 이미지마다 출처·라이선스 기록, alt 텍스트 있음
- YMYL 주제(건강·금융·법률)면 "기준일"과 공식 출처 링크 포함

## 5. 리포지토리 구조

이 저장소(`codingStudy.github.io`)는 공개 GitHub Pages 학습용이라, 실제 에이전트는 **새 private 저장소**(예: `tistory-agent`)에 두는 걸 권장한다. 초안, 성과 데이터, 나중에 붙일 수 있는 로그인 세션 파일이 공개되면 안 되기 때문이다.

```
tistory-agent/
├─ CLAUDE.md                      # 블로그 정체성, 말투, 금지 사항, 파이프라인 규칙
├─ .claude/
│  ├─ settings.json               # im-not-ai 플러그인 등록, 권한 설정
│  ├─ skills/
│  │  ├─ new-post/SKILL.md        # /new-post "키워드" — ①~⑨ 오케스트레이터
│  │  ├─ plan-week/SKILL.md       # 키워드 리서치, 주간 백로그
│  │  ├─ tistory-format/SKILL.md  # 마크다운 → 티스토리 HTML, SEO 패키지
│  │  ├─ refresh-post/SKILL.md    # 기존 글 업데이트
│  │  └─ weekly-report/SKILL.md   # 성과 분석
│  └─ agents/
│     ├─ researcher.md            # 웹 검색·공식 자료 수집, 출처 기록
│     ├─ writer.md                # 아웃라인·초안
│     ├─ fact-checker.md          # 초안 ↔ 리서치 대조
│     └─ seo-editor.md            # 제목·설명·태그·내부 링크
├─ config/
│  ├─ blog.yaml                   # 카테고리, 발행 빈도, 길이 범위, 금칙어, im-not-ai 버전
│  ├─ style-guide.md              # 말투·문장 길이·예시 문단 (본인이 쓴 글 3편 기반)
│  └─ templates/                  # 글 유형별 아웃라인 (howto, guide, compare, review, checklist)
├─ data/
│  ├─ backlog.csv                 # 키워드, 의도, 유형, 시즌, 우선순위, 상태
│  ├─ published.json              # 발행 글 URL·제목·키워드 (내부 링크, 중복 방지)
│  └─ reports/                    # Search Console·애드센스 CSV
├─ posts/
│  └─ 2026-11-03-연말정산-간소화/
│     ├─ 00_brief.md  01_research.md  02_experience.md  03_outline.md
│     ├─ 04_draft.md  05_factcheck.md  06_humanized.md
│     ├─ post.html  meta.json  qa.json  images/
├─ scripts/
│  ├─ md_to_tistory.py            # 티스토리 에디터 HTML 모드용 변환 (표·목차 스타일 포함)
│  ├─ qa_check.py                 # ⑨ 체크리스트
│  ├─ make_thumbnail.py           # 제목 텍스트 썸네일 (라이선스 확인된 폰트만)
│  ├─ update_published.py         # 발행 후 URL 기록
│  └─ publish_draft.py            # (선택) Playwright로 임시저장까지만
└─ _workspace/                    # im-not-ai 실행 산출물 (.gitignore)
```

### CLAUDE.md에 들어갈 핵심 규칙 (초안)

```markdown
# 이 저장소의 목적
lifegoals001.com 티스토리 블로그 글을 만든다. 사람이 검토하기 전까지는 어떤 글도 공개 발행하지 않는다.

# 글 원칙
- 독자의 검색 의도에 첫 문단에서 바로 답한다.
- 사실·수치·날짜는 data 출처가 있는 것만 쓴다. 출처 문장을 그대로 옮기지 않는다.
- 02_experience.md가 있으면 그 내용을 본문에 녹인다. 없는 경험을 지어내지 않는다.
- 건강·금융·법률 주제는 기준일과 공식 출처를 적고, 단정 대신 조건을 쓴다.
- 말투는 config/style-guide.md를 따른다.

# 파이프라인
- /new-post 순서를 건너뛰지 않는다. 사실 검증(⑥) 전에 윤문(⑦)하지 않는다.
- 윤문은 /humanize-korean 장르: 블로그로 하고, 게이트 결과를 qa.json에 기록한다.
- 하루에 만드는 공개 예정 글은 최대 2편.
```

## 6. 콘텐츠 전략

### 주제 고르기

블로그 접속이 안 돼서 현재 카테고리를 보지 못했다. 도메인 이름(lifegoals)과 애드센스 단가를 같이 놓고 보면 아래 후보가 자연스럽다. 기존 글과 본인이 실제로 아는 분야에 맞춰 1~2개를 주력으로 정한다.

| 후보 | 트래픽 | 광고 단가 | 경쟁 | 필요한 것 |
|---|---|---|---|---|
| 정부 지원금·제도·신청 방법 | 높음 (시즌성 큼) | 중~높음 | 높음 | 공식 공고 확인, 신청 기간 맞춘 선발행 |
| 세금·연말정산·절세 | 시즌에 급증 | 높음 | 높음 | 기준 연도 명시, 계산 예시 |
| 재테크 기초 (예적금·청약·연금) | 중간 | 높음 | 중간 | 금리·조건 기준일 관리, 투자 권유 금지 |
| 자기계발·목표 관리·생산성 도구 | 중간 | 중간 | 낮음~중간 | 직접 써 본 경험이 차별점 |
| 생활 정보 (가전·통신비·보험 비교) | 중간 | 중~높음 | 중간 | 비교표, 제휴 수익과 궁합 좋음 |

권장 비율: 꾸준히 검색되는 글 70%, 시즌·이슈 글 30%. 시즌 글은 검색량이 오르기 2~4주 전에 발행한다 (예: 연말정산은 12월 말~1월 초).

### 글 유형 템플릿 (`config/templates/`)

1. 방법형: 결론 요약 → 준비물·조건 → 단계별 방법(스크린샷 자리) → 자주 막히는 곳 → FAQ
2. 총정리형: 한 줄 요약 → 대상·조건·기간 표 → 항목별 설명 → 공식 링크 → FAQ
3. 비교형: 누구에게 무엇이 맞는지 결론 → 비교표 → 항목별 차이 → 추천 대상
4. 경험형: 상황 → 직접 해 본 과정 → 결과·비용·시간 → 아쉬운 점 → 팁
5. 체크리스트·계산형: 체크리스트 → 계산 예시 2~3개 → 주의 사항

공통: 첫 3줄에 답, 목차, 표 1개 이상, FAQ 3~5개, 관련 글 링크 2~3개.

### 수익 보강

- 광고 배치: 티스토리 수익 메뉴에서 애드센스 자동광고 + 본문 상·하단 정도로 시작한다. 광고 밀도가 높으면 체류 시간이 줄어 오히려 손해다.
- 제휴: 비교형·생활 정보 글에 쿠팡 파트너스 같은 제휴 링크를 붙일 수 있다. 대가성 문구 표기는 필수이고, `qa_check.py`가 확인한다.
- 리라이트: 노출은 많은데 클릭률이 낮은 글은 제목을, 8~20위에 머무는 글은 본문을 보강한다. 새 글보다 효율이 좋은 경우가 많다.

## 7. 발행 방식 (3단계 선택지)

| 방식 | 내용 | 장점 | 위험 |
|---|---|---|---|
| A. 붙여넣기 (권장 시작점) | `post.html`을 티스토리 에디터 HTML 모드에 붙여넣고, 대표 이미지·카테고리·태그 지정 후 예약 발행 | 안전, 구현 쉬움 | 글당 3~5분 수작업 |
| B. 반자동 임시저장 | 처음 한 번 직접 로그인해 세션을 저장하고, Playwright가 제목·본문·태그를 넣어 **임시저장 또는 비공개**까지만 처리. 공개 전환은 사람이 | 수작업 1~2분으로 감소 | 화면 변경 시 고장, 카카오 로그인 보안 확인, 자동화에 대한 약관 위험. 저빈도·본인 PC에서만 |
| C. 완전 자동 공개 | 사람 확인 없이 공개 발행 | — | 비권장. 품질 사고와 정책 위반이 그대로 노출됨 |

B를 하더라도 로그인 세션 파일은 절대 커밋하지 않는다(`.gitignore`). 클라우드 세션은 네트워크 정책에 따라 티스토리 접속이 막힐 수 있어서(이번 세션도 차단됨) B는 본인 PC에서 돌리는 걸 기본으로 한다.

## 8. 실행 위치와 자동화 수준

| 단계 | 실행 방법 | 사람 개입 |
|---|---|---|
| 1단계 (MVP) | 로컬 Claude Code에서 `/new-post "키워드"` 수동 실행 | 주제 선정, 검토, 발행 |
| 2단계 (배치) | `/plan-week`로 5편 주제 확정 → 한 번에 ①~⑨ 실행 | 주 1회 주제 승인 + 글별 검토 |
| 3단계 (예약 실행) | Claude Code 예약 작업(클라우드) 또는 로컬 cron + `claude -p`로 매일 아침 1~2편 생성 → 검토 대기함에 적재 | 휴대폰으로 검토·승인, 발행 |

검토 대기함 후보:

- 로컬 폴더: 가장 단순. PC 앞에서만 검토 가능
- GitHub PR: 글 하나당 PR 하나, 휴대폰 GitHub 앱으로 읽고 코멘트, 병합 = 승인
- Notion 데이터베이스: 상태(아이디어→리서치→초안→검토 대기→발행 완료)를 콘텐츠 캘린더로 관리. 이 계정에 Notion 연결이 이미 있어서 붙이기 쉽다

비용: im-not-ai 런타임 에이전트는 기본 `model: opus`로 정의돼 있고, 경로에 따라 1~3콜을 쓴다. 리서치·초안까지 합친 글당 사용량은 1주차에 실측해서 구독 사용량 안에서 돌릴지, 모델을 조정할지 정한다.

## 9. 성과 피드백 루프 (`/weekly-report`)

1. 입력: Search Console 실적(쿼리·페이지별 노출·클릭·순위), 애드센스 페이지별 수익, 티스토리 유입 키워드. 처음에는 CSV를 `data/reports/`에 넣는 방식으로 시작하고, 익숙해지면 Search Console API로 바꾼다.
2. 분석:
   - 노출 많고 CTR 낮은 글 → 제목·설명 리라이트 후보
   - 평균 순위 8~20위 글 → 본문 보강 후보 (`/refresh-post`)
   - 노출되는데 전용 글이 없는 쿼리 → 새 주제 후보
   - 카테고리별 RPM → 다음 달 주제 비중 조정
3. 출력: 주간 리포트 1장 + `backlog.csv` 갱신 제안 (반영은 사람이 승인)

## 10. 위험과 안전장치

| 위험 | 안전장치 |
|---|---|
| 대량 저품질 판정 (검색·애드센스) | 하루 최대 2편, 글마다 1차 정보 1개 이상, 사람 승인 필수, 품질 등급 기록 |
| 사실 오류 (특히 금액·기간·조건) | ⑥ 사실 검증 + 윤문 후 수치 재대조, 기준일 표기, YMYL은 공식 출처만 |
| 저작권 (기사 문장·이미지·폰트) | 출처 문장 연속 일치 검사, 이미지 라이선스 기록, 직접 찍은 사진 우선, 썸네일 폰트는 상업 이용 가능한 것만 |
| 무효 트래픽 | 본인 광고 클릭 금지, 트래픽 교환·자동 방문 도구 사용 금지 |
| 티스토리 운영 정책 | 공개 발행은 사람이, 자동화는 임시저장까지, 짧은 간격 연속 발행 금지 |
| 제휴 표시 누락 | 제휴 링크 있으면 대가성 문구 없을 때 QA 실패 처리 |
| im-not-ai 과윤문·의미 변형 | 스킬 자체 게이트(변경률·수치·서법) + 우리 쪽 H2·수치 재검사, 실패 시 초안으로 되돌림 |
| 경험 위조 | 에이전트는 `02_experience.md`에 없는 경험담을 쓰지 않는다 (CLAUDE.md 규칙) |

im-not-ai 설명에 "AI detector bypass" 같은 트리거가 들어 있지만, 이 계획에서는 읽기 좋은 문장을 만드는 용도로만 쓴다. 구글은 AI 판별기 점수로 순위를 매기지 않는다. 문체를 사람처럼 바꿔서 저가치 글을 숨기는 전략은 통하지 않는다고 보고 설계했다.

## 12. 첫 주에 만들 `/new-post` 스킬 뼈대

```markdown
---
name: new-post
description: 키워드 하나로 티스토리 글 한 편을 검토 대기 상태까지 만든다. "/new-post 키워드" 또는 "새 글 써줘".
---

1. posts/{오늘날짜}-{slug}/ 폴더를 만들고 00_brief.md를 쓴다.
   published.json에 같은 키워드가 있으면 멈추고 알린다.
2. researcher 에이전트로 01_research.md를 만든다 (사실마다 출처 URL·확인 날짜).
3. 경험 질문 3개를 사용자에게 보여 주고 02_experience.md에 답을 받는다.
   답이 없으면 "경험 없음"으로 적고 계속한다.
4. writer 에이전트로 03_outline.md → 04_draft.md를 쓴다.
   config/style-guide.md와 im-not-ai quick-rules.md를 함께 읽고 쓴다.
5. fact-checker 에이전트로 05_factcheck.md를 만들고 초안을 고친다.
6. /humanize-korean 장르: 블로그 (헤딩·표 구조 유지)로 윤문한다.
   게이트 exit 코드와 등급을 qa.json에 기록한다. exit 2나 등급 C/D는 4장 규칙대로 처리한다.
7. tistory-format 스킬로 post.html·meta.json을 만든다.
8. scripts/qa_check.py를 돌린다. 실패 항목이 있으면 고치고 다시 돌린다 (최대 2회).
9. 검토 대기함에 올리고, 사람이 봐야 할 점(확인 필요 표시, 게이트 경고)을 요약해 보고한다.
```

## 13. 구현 전에 정해야 할 것

1. 주력 카테고리 1~2개 (기존 글 목록이나 카테고리 화면을 공유해 주면 반영)
2. 실행 위치: 로컬 PC의 Claude Code / Claude Code 클라우드 세션 / 둘 다
3. 발행 방식: A(붙여넣기)로 시작할지, B(임시저장 자동화)까지 갈지
4. 검토 대기함: 로컬 폴더 / GitHub PR / Notion
5. 저장소: 새 private 저장소(권장) / 이 저장소의 하위 폴더
6. 제휴 수익(쿠팡 파트너스 등) 병행 여부
